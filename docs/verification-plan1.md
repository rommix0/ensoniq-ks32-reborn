## Effect-style ESP programs (`tests/test_esp_programs.cpp`)

The ESP2 document's algorithms (Part III) are written for a different instruction set. Both
programs are re-expressed with ES5510 words (`esp::Instr{...}.encode()`) and respect the
pipeline of decisions E17/E18: an ALU result reaches the multiplier two words later, a RAM read
lands in DIL two words after the issuing word, the DOL FIFO is two deep, and an ALU write to
MACH is the preload for the next word's accumulate. Both were checked with `esp_dis`.

### `esp_allpass_reverb_decays`

- **Topology** (ESP2 Part III §7, Figure R, reduced): the four input diffusers in series, then
  one recirculating tank delay. The diffusers are lattice allpasses with lengths 142, 107, 379
  and 277 samples and coefficients 0.75, 0.75, 0.625 and 0.625 (DIFFUS1/DIFFUS2). The tank is
  `t = u + 0.7 * t[n - 4453]`, where 4453 is the tank's longest line in Figure R.
- **Code**: 18 words. Each allpass is the ESP2 two-line lattice `w = x - g*d` (written to the
  line) and `y = d + g*w`. It takes three ES5510 words, using the MAC preload the way ESP2's
  `MOV ... > MACP` does.
- **Machine setup**: SIGREG bit 22 = 1 (multiplier shift 1, as the KS-32 sets it), MEMSIZ
  0x0000FF, DLENGTH 0xFFFF00 (the whole 64K-word DRAM is the delay ring), DBASE 0.
- **Outputs**: SER3L = `t` (wet). SER3R = `u` (the diffusers only, no feedback).
- **Stimulus**: one full-scale sample (0x7FFF) on SER0L, then zeros, for 6 s at 29 761.7 Hz
  (the KS-32 frame rate, OTIS 15.238 MHz / 512).
- **Measure**: split the output into 0.1 s windows (2976 frames) from frame 0. The decay time
  is the end of the last window whose RMS is at or above −60 dBFS (32.768 LSB of 16-bit full
  scale). The result has 0.1 s resolution.

| Output | −60 dBFS time | Pinned |
|---|---|---|
| Wet (SER3L) | **1.3 s** | `CHECK_EQ(wetT, 13)` and `CHECK(wetT < 30)`, the guard against MAME bug #1 |
| Diffusers only (SER3R) | 0.2 s | `CHECK_EQ(dryT, 2)` |

The guard catches long tails. With the feedback mutated to 0.97, the test fails: the wet tail
is still above −60 dBFS at the end of the 6 s run.

The wet output never reaches exactly zero. From about 2.6 s on it settles into a zero-input
limit cycle of about 2 LSB RMS (−84 dBFS). This is expected. The DOL write floors 24 bits to 16 (E18,
which matches MAME's hardware test in PR #15537). The ESP2 text explains that such lattice and
feedback networks keep limit cycles unless magnitude truncation is used, and the ES5510 does not
have it.

### `esp_chorus_interp_lsb`

This is the ESP2 Part III §1.2 linear interpolation kernel:
`out = frac_u * D[m] + frac * D[m+1]`.

- The tap offset GPR holds `m` in bits 23..8 and an 8-bit fraction in bits 7..0. The AGEN
  ignores the fraction bits (MEMSIZ 0xFF).
- `LS15` turns the fraction into a positive Q23 coefficient (E14). `DIFF` forms `frac_u`
  (E2).
- The program computes the `m+1` tap offset itself and reads both taps through the delay
  addressing.

The fraction is swept from 0 to 255/256, then on to the next whole tap. The taps hold −0x4000,
+0x4000 and +0x4000. The output rises strictly in 256 equal steps of 0x8000 (24-bit), each within
±1 LSB. It starts at D[m] and ends at D[m+1] − 1 LSB (`frac_u` = 1 − 2^-23).

## Reverb decay: ours vs MAME (`tests/data/reverb_tank.trace`)

**Input.** The trace format cannot write SER0 directly. The impulse comes from two one-shot OTIS
voices on CA 1 that play word 0 = 0x7FFF once. The filter poles are fully open (K = 0xFFF0) and
the volume is exponent 15, mantissa 0. The pair gives 32734 on SER0L in frame 0 (MAME: 32735),
followed by a few LSB of filter tail. Main L in frame 0 is 32734 × 0.75² × 0.625² = 7192.

**Run.** The program is loaded through host writes while the ESP is halted. The trace then runs
60 s (1 785 714 frames). Each output is measured with
`python -I tools/mame_ref/analysis/decay_time.py <pcm> <channel>`, which uses the same measure
as the test.

| Output | Ours (`ens_trace`) | MAME (`mame_ref`) |
|---|---|---|
| Main L (wet), −60 dBFS time | **1.3 s** | **1.3 s** |
| Main R (diffusers only), −60 dBFS time | 0.2 s | 0.2 s |
| Main L, RMS of the last 0.1 s window (at 60 s) | 2.097 LSB (−83.9 dBFS) | 2.100 LSB (−83.9 dBFS) |
| Main L peak | 7192 | 7192 |

**MAME's long-tail bug is not reproduced by this program.** On this ES5510 reverb, MAME's tail
decays exactly as fast as ours: the 45 s versus 2 s behaviour of the SD-1's FLANGE+DLY+REV
does not appear.

The two outputs are not bit-identical (see the next section). To show that the differences come
from the OTIS side and not from the ESP, we ran a replay experiment. It used a scratch build
that is not committed.

1. A variant of the trace adds two copies of the impulse voices on CA 0, so aux L shows exactly
   the SER0L input that each implementation gives its ESP.
2. That variant ran in MAME for 200 000 frames (6.7 s).
3. Our `Esp` core was fed MAME's SER0 input, frame by frame.

Our main L/R then equalled MAME's main L/R in every frame, with 0 frames differing. On this
program, MAME's ES5510 and ours agree bit for bit, including the following:

- the MAC preload slot (E17);
- the MACH splice that keeps the low 24 bits (E6);
- the MUL truncation;
- the DOL floor and the two-deep FIFO (E18);
- the DIL timing (E18);
- delay addressing over a 64K ring with DBASE reloads (E7).

So whatever drives the SD-1 tail lies on a path this program does not use. Candidates already
listed in `docs/mame-ref.md`, none confirmed here:

- MAC overflow: MAME keeps `machl` unwrapped (E6, audit §2.4).
- A skippable word directly after the flag-setting word (E17).
- A one-operand op with a DIL operand select.
- Block-granular host timing.
- The OTIS-side residue below.

One observation from this run: MAME's truncating OTIS filter (audit §1.4) does not decay to
zero while a voice plays. In the replay variant, MAME's ESP input (two voices) is 32735, 32, then
a constant 4 LSB until the voices stop at frame 511, after which MAME's stopped voices output
nothing (O7). Ours is 32734, 28, then 0 from frame 2. This trace cannot tell whether such a
residue matters for the SD-1 tail.

## Cross-toolchain identity

`ens_trace` was built twice: with MinGW i686 (`build/ens_trace`) and with MSVC x64 (the VS build
tree's `Release/ens_trace`). Both binaries ran the same traces, and `pcm_diff` compared their
outputs. The files were also compared byte for byte with `cmp`.

| Trace | Frames | `pcm_diff` MinGW vs MSVC | Exit |
|---|---|---|---|
| `tests/data/smoke.trace` | 64 | identical (byte-identical) | 0 |
| `tests/data/esp_mix.trace` | 96 | identical (byte-identical) | 0 |
| `tests/data/reverb_tank.trace` | 1 785 714 | identical (byte-identical, 14 285 712 bytes) | 0 |

The pinned reverb decay (1.3 s and 0.2 s) and every other test also pass on both toolchains, so
the chip-rate output is bit-identical between 32-bit MinGW and 64-bit MSVC, as the Global
Constraints require.

## Low-confidence decisions for Plan 3 and later to revisit

These are the entries in `docs/decisions.md` rated Low or Low-medium, or Low in part. Plan 2
(the ROM investigation, already done in `docs/rom-investigation`), Plan 3 (the MIDI test player)
and the firmware-emulation project after it can confirm or refute most of them by observing what
the firmware relies on, or by testing on hardware.

| Id | Topic | Current choice | What would settle it |
|---|---|---|---|
| O8 | IRQ/IRQV | IRQV read `0x60 \| (pending?0:0x80) \| vec`, bits 6:5 read 1; the vector reload cycle is inferred | Firmware IRQ handler behaviour; a hardware read of IRQV |
| O10 | OTIS reset state | All voice registers 0 except CR = 0x0003, ACT 31, SERMODE A/D = 1 | Only A/D is documented; check what the firmware assumes before it initialises |
| E6 | MAC model (Low-medium) | 50-bit wrap, sat48 readout; the "MACL dest duplicates upper half" sentence is not implemented | Firmware programs that overflow the MAC; a hardware test |
| E7 refinements (1), (2) (Low-medium) | Delay RAM compare and wrap | Delay compare and wrap on address bits only; DBASE reload masked | Unstated edge; KS-32 uses DLENGTH 0xFFFFFF with MEMSIZ 0xFF, so watch the ring period in Plan 2 |
| E17 (CCR-destination detail: Low; MAC preload slot: Medium) | CCR destination and MAC preload | An explicit CCR destination overrides the flag update | Any firmware program that writes CCR directly |
| E20 | MEMSIZ write effect on DBASE | MEMSIZ write sets `DBASE &= ~MEMSIZ` | Only "affects DBASE directly" is documented |
| E9 | Unassigned addresses 192..233 | Addresses 192..233 read 0 and ignore writes | Undocumented; check whether any firmware program touches them |
| E10 | Host DOL low byte | Host DOL low byte reads 0x00 (the text) rather than 0xFF (the table) | Firmware read-back of DOL |
| E11 | Program without END | Program without END: word 159 acts as END | Undocumented; firmware programs all have END, so this matters only for corrupt loads |
| E22 | SPR read-back width | Narrow SPR read-back (SIGREG bit 22, CCR 23..19, CMR 23..18) | Firmware read-back and verify of SIGREG (it writes all ones) |
| E23 | ESP reset contents | ESP reset clears GPRs and program memory | Real power-on contents are unknown; the firmware loads everything anyway |
| E24 (pipeline discard: Low) | Halt-enable write mid-program | A halt-enable write mid-program discards the in-flight pipeline | Effect switching in Plan 2: listen for clicks or stale words at program changes |
| E28 (Low-medium) | Idle-step contents | A host transfer and the clear/refresh step share one idle step | Timing of program loads and RAM clears while halted (Task 9 note: a RAM clear can overrun tables the host writes early) |
| E29 | Serial control and test registers | Serial control register and test-only registers are stored, not acted on | The firmware only writes 0x63; serial formats matter only if Plan 2 models the serial layer |

Related open points from the Plan 1 reviews (`progress.md`) that Plan 2 should also check:

- The trace runner has zero serial-frame latency. Hardware adds at least one frame.
- `idleStep()` must be driven at the hardware rate while the ESP is halted.
- The UTF-8 BOM is not skipped in trace files.
- Before Plan 3: add a slots-per-sample advance API (E30); top of firmware plan: check routine 0xC1CC80 read-back of $F4/$F9 vs E22 (ruling R18).

## Reproduce

```bash
cmake -S . -B build -G Ninja -DCMAKE_BUILD_TYPE=Release && cmake --build build
ctest --test-dir build --output-on-failure
cmake -S . -B build-msvc -G "Visual Studio 17 2022" -A x64
cmake --build build-msvc --config Release
ctest --test-dir build-msvc -C Release --output-on-failure
cmake -S . -B build-ref -G Ninja -DCMAKE_BUILD_TYPE=Release -DENS_BUILD_MAME_REF=ON
cmake --build build-ref

python -I tools/mame_ref/analysis/make_reverb_tank_trace.py tests/data   # regenerates the trace
build/ens_trace tests/data/reverb_tank.trace ours.pcm
build-ref/mame_ref tests/data/reverb_tank.trace mame.pcm
build/pcm_diff ours.pcm mame.pcm
python -I tools/mame_ref/analysis/decay_time.py ours.pcm 2      # main L (wet)
python -I tools/mame_ref/analysis/decay_time.py mame.pcm 2
```

For the cross-toolchain check, run the MSVC `ens_trace` (in the `Release` configuration
directory of `build-msvc`) on the same trace and compare its output with `pcm_diff`.
