# KS-32 Machine Implementation Plan (Plan 6)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build the emulated KS-32: an MC68681 DUART model, a front-panel model and a `Machine` that joins them with the 68000, OTIS, ESP, RAM and ROM. The user's OS ROM must boot to its play screen and play its factory sounds from a MIDI file and from live MIDI, driven from a headless runner, `ks32emu`.

**Architecture:**
- **New library `ens_duart`.** `src/duart/` holds a datasheet-based MC68681 model: two serial channels with character timing, the counter/timer, the input and output ports and vectored interrupts.
- **`ens_ks32` gains `Machine` and `Panel`.**
  - `Machine` owns the CPU, the existing `Board` (OTIS, ESP and delay DRAM), the DUART, the RAM, the ROM and the panel.
  - It decodes the 68000 bus and runs everything in one-voice-slot slices.
  - It reports every device access to an optional bus-trace hook.
- **The hardware facts come from evidence, not decompiling** (design §8). Tasks 3–8 find each fact by running the firmware and reading the bus trace, then pin it with a test and record it in `docs/ks32-hardware-interface.md`. The facts are the memory map, the interrupt levels, the panel protocol, the analog inputs and the MIDI channel.
- **`ks32emu` is the headless runner.** It boots the ROM, prints the display, records traces, renders a MIDI file to WAV and plays live, reusing `ks32play`'s WinMM, WASAPI and file code.

**Tech Stack:**
- C++17 and CMake 3.20+, with `tests/check.h`.
- No third-party libraries.
- References:
  - the KS-32 service manual (`datasheets/ks32.pdf`);
  - the MC68681 DUART data sheet (downloaded with permission in Task 1);
  - the M68000 manuals (already in `datasheets/`);
  - the OTIS and ESP notes;
  - `docs/rom-investigation/findings.md`.

**Spec:** `docs/design/2026-10-21-ks32-machine-and-juce-app-design.md` ("design"), revised 2026-10-23 and approved. Plan 6 is the design's §9 row 6. It builds §7 layers 2–4 and goal 2 (§2), finds the §8 facts and settles open items A–F of §10.

## Global Constraints

- **Pure emulation code.** `src/duart` and `src/ks32` are C++17 with:
  - no JUCE, no OS calls, no threads and no file I/O;
  - no mutable globals or statics;
  - no `float` or `double`.

  State must be bit-identical across the MSVC x64 and MinGW i686 builds (design §5, §6). File I/O, threads, WinMM and WASAPI live in `tools/ks32emu` only.
- **Builds.** Everything builds without warnings with VS 2022 x64 (`build-msvc/`, `/W4`) and with MinGW g++ 14 plus Ninja (`build/`, `-Wall -Wextra`). The MinGW executables run from PowerShell, not Git Bash.
- **No decompiling** (the user's ruling, 2026-10-23):
  - **Where facts come from.** The service manual, the datasheets, `findings.md`, and bus traces of the running firmware: device accesses, interrupt acknowledges, exception counts and PC addresses.
  - **The debug disassembler (`m68k::disassemble`)** may be used only to see where the *emulator* is stuck. It is never used to work out what the firmware does.
  - **Nothing ROM-derived is committed.** That covers no listing, no trace file, no ROM bytes and no byte dumps of ESP programs or sound data.
  - **What docs and tests may quote:** register-level facts (addresses, register values, baud settings) and short display strings. Use the service manual's wording where it gives one, plus the observed play-screen text needed to pin the boot.
- **MAME.** MAME is a comparison point only (design §5). A fact is decided from the evidence first. `docs/ks32-hardware-interface.md` may then add "MAME agrees" or "MAME differs".
- **Downloads.** Each needs the user's explicit permission. The controller asks in Task 1, Step 0.
- **ROM tests.** Tests that need the ROMs use `ENS_ROM_DIR`:
  - the OS is in `ks32/ks32v301upper.bin` and `ks32/ks32v301lower.bin`;
  - the wave ROMs are `sq1-u25.bin`, `sq1-u26.bin`, `rom2.u39` and `rom3.u38`.

  Without them a test prints `  skip: ROMs not found` and passes.
- **Never committed:** ROMs, traces, firmware listings, service-manual images, `docs/Ensoniq_KS32_Top.png` and `session_memory.json`.
- **Decisions.** Every choice the references do not settle is marked `// DECISION <id>: <one line>` at the point of use. Each gets a `docs/decisions.md` entry (options, choice, evidence, confidence, status):
  - `## DUART` holds D1 onward;
  - `## KS-32 machine` holds K1 onward.

  The defaults are in the table below. New ids continue in order of discovery.
- **Stop and ask.** If the evidence contradicts this plan or the design, or a fact cannot be settled with a task's procedure, the implementer stops and reports. The controller then asks the user, and nothing is guessed silently.
- **Branch.** Work on branch `plan6-ks32-machine` in a worktree, and commit after each task.

## Decision Defaults

| Id | Topic | Default (my call unless noted) | Task |
|---|---|---|---|
| D1 | Serial timing | Character level. A character takes (1 start + data bits + parity bit if enabled + stop bits) × bit time. There is no bit-level line, no break detection and no receive parity or framing errors. | 1 |
| D2 | Receive path | Bytes the machine queues enter the receiver one per character time, at the channel's receive rate. They are lost while the receiver is disabled. The FIFO is 3 deep plus the shift register; overrun follows the data sheet. | 1 |
| D3 | Unmodelled features | These are not modelled: echo and loopback channel modes, RTS/CTS control, multidrop, break commands, external IP clocks, and OPCR special outputs. A write that selects one increments `unsupportedWrites()`, and the boot test requires 0. Task 7 adds a feature only if the firmware uses it. | 1, 3 |
| D4 | Reset state | As the data sheet gives it. IVR = 0x0F. Output-port pins high (OPR = 0). | 1 |
| D5 | Time base | `advance()` counts whole X1 clocks. The C/T's X1/16 prescaler is counted exactly across calls. | 1 |
| K1 | Memory map | Settled in Task 3. Task 2's provisional map: <br>- ROM at 0xC00000–0xC3FFFF: upper EPROM = even bytes; lower EPROM = odd bytes, mirrored every 0x20000. <br>- 64 KB RAM (service manual p1) at 0xFF0000–0xFFFFFF, mirrored at 0x000000–0x00FFFF. Reads of 0x000000–0x000007 come from ROM 0xC00000–7 until the first write into that range. <br>- OTIS at 0x200000–0x20001F (words, reg = A4..A1). <br>- ESP at 0x260000–0x2601FF (odd bytes, reg = A8..A1). <br>- DUART at 0x280000–0x28001F (odd bytes, reg = A4..A1). | 2, 3 |
| K2 | Interrupt map | Settled in Task 3: the 68000 level of the OTIS IRQ and of the DUART INTR, and how each answers the acknowledge. Task 2 wires both at level 0 (off). | 2, 3 |
| K3 | Clocks | The CPU and OTIS run at 15 238 090 Hz (30 476 180 / 2). A voice slot is 16 CPU clocks. The DUART X1 clock is 4 000 000 Hz. The ESP runs 89 instruction periods per frame (P1). Confirmed in Task 3 by the boot clock test (32 voices) and in Task 7 by the MIDI rate: 31 250 baud is 128 X1 clocks per bit. (Design §7; the clocks are MAME's values, to be confirmed.) | 2, 3, 7 |
| K4 | Scheduler | Each slot runs `cpu.run(16 - carry)` and carries the overshoot. A carry of 16 or more skips the CPU for that slot. Then: <br>- `otis.stepVoice()`; <br>- the DUART advances by an exact rational X1 accumulator; <br>- the ESP advances per K5; <br>- IPL is recomputed. <br>IPL is also recomputed after every device write. | 2 |
| K5 | ESP cadence | While running, the ESP gets `esp.advance(89)` at the end of the frame (as `Board::frame`). While halted, slot i of an N-slot frame (N = ACT + 1) gets floor(89·(i+1)/N) − floor(89·i/N) `idleStep()` calls. | 2 |
| K6 | Unmapped accesses | Reads return 0 and writes are ignored. Every one is traced. The boot test requires none, so every address the firmware uses must be in the K1 map. | 2, 3 |
| K7 | Panel protocol | Settled in Tasks 4–5 from the trace. The panel answers with no processing delay of its own, and its bytes enter the DUART at the line rate (D2). | 4, 5 |
| K8 | Analog inputs | Settled in Task 6. A conversion completes at once when the input selection changes; the datasheet's 1.6 ms is not modelled. | 6 |
| K9 | Wait states | None (design open item F). This is revisited only if the trace shows a timing failure. | 3 |
| K10 | Memory card | The slot is always empty (design open item E). | 8 |
| K11 | Battery RAM image | The whole battery-backed RAM (K1), stored as raw bytes. A cold start is zero-filled. | 8 |
| K12 | Local keyboard | Its path is documented. It is implemented only if it rides a path the machine already models (the panel link or the analog inputs). Otherwise playing goes through MIDI in. | 8 |
| K13 | Resting analog values | Pitch wheel at centre, mod wheel 0, CV pedal unplugged, volume at maximum (so headless renders are audible), data entry at mid, pressure 0, battery nominal. | 6 |
| K14 | RESET instruction | Settled in Task 3: which devices the RESET line resets. Task 2 resets the DUART only. | 2, 3 |
| K15 | ESPHALT | DUART OP6 drives `Esp::setHaltPin` (findings B). The polarity is settled in Task 3. | 3 |

## Review Focus

1. **Real-time headroom.** The JUCE app (Plan 7) runs the machine inside an audio callback. `ks32emu bench` must report at least 2.0× real time on the MSVC x64 Release build (Task 9). If it does not, stop: the slice size is a design call.
2. **Two-button combinations and quick taps.** The service procedures hold one button while pressing another: Edit Seq/Preset, then Bank 9, then Screen n. A press and release inside one character time must not be lost either. Tests: `ks32_firmware_version_screen` and `ks32_firmware_quick_tap_is_seen` (Task 5).
3. **MIDI bursts.** A chord, a running-status stream or a program change arriving all at once is paced at 31 250 baud. It must never overrun the DUART or produce "out of buffers" (event 144). Test: `ks32_firmware_midi_burst_no_overrun` (Task 7).
4. **Cold start and saved RAM.** Blank RAM must boot to the play screen with no low-battery or unexpected-event message. A saved RAM image must boot back to the same state. Tests: `ks32_firmware_cold_boot_is_clean` (Task 6) and `ks32_firmware_ram_image_keeps_selected_sound` (Task 8).
5. **Missing or wrong ROM files.** `Machine::create` rejects a wrong size and names the file, and `ks32emu` exits 2 with that message instead of crashing. Test: `ks32_machine_rejects_wrong_rom_size` (Task 2).

**Interfaces:**
- Produces (namespace `ens::duart`):
  ```cpp
  class Duart {
  public:
      explicit Duart(uint32_t x1Hz);           // crystal frequency; the KS-32 passes 4'000'000 (K3)
      void reset();                            // RESET pin: data-sheet reset state (D4)
      uint8_t read(uint8_t reg);               // reg 0..15 = A4..A1, with the data-sheet read side effects
      void write(uint8_t reg, uint8_t v);
      void advance(uint32_t x1Clocks);         // baud timing, C/T, character shifting
      bool irq() const;                        // INTR asserted: (ISR & IMR) != 0
      uint8_t ivr() const;                     // vector answered on interrupt acknowledge
      uint8_t outputPins() const;              // OP7..OP0 pin levels (pin = NOT OPR bit)
      void setInputPins(uint8_t ip);           // IP5..IP0 levels, bit set = high
      void receive(int ch, uint8_t byte);      // ch 0 = A, 1 = B: queue a character on RxD (D2)
      std::vector<uint8_t> takeTransmitted(int ch);  // characters that finished leaving TxD
      uint32_t rxBitClocks(int ch) const;      // X1 clocks per receive bit, 0 if unclocked
      uint32_t overruns(int ch) const;         // characters lost to overrun since reset
      uint32_t unsupportedWrites() const;      // D3
  };
  ```
- Register map, to check against the data sheet before coding:
  - **Reads:** 0 MR1A/MR2A, 1 SRA, 3 RHRA, 4 IPCR, 5 ISR, 6 CUR, 7 CLR, 8 MR1B/MR2B, 9 SRB, 11 RHRB, 12 IVR, 13 IP, 14 start-C/T command, 15 stop-C/T command.
  - **Writes:** 0 MR1A/MR2A, 1 CSRA, 2 CRA, 3 THRA, 4 ACR, 5 IMR, 6 CTUR, 7 CTLR, 8 MR1B/MR2B, 9 CSRB, 10 CRB, 11 THRB, 12 IVR, 13 OPCR, 14 set OP bits, 15 reset OP bits.
  - **Bits.** SR bit 0 RxRDY, 1 FFULL, 2 TxRDY, 3 TxEMT, 4 OE. ISR bit 0 TxRDYA, 1 RxRDYA/FFULLA, 3 counter ready, 4 TxRDYB, 5 RxRDYB/FFULLB, 7 input-port change.
  - **Baud rates.** Each CSR code is an integer X1 divisor of the 16× clock, from the data sheet's table at 3.6864 MHz (for example 9600 baud → 24). Rates scale with X1. The C/T as a baud source is the C/T output.

- [ ] **Step 0 (controller): Ask about the download.** Ask the user's permission to download the MC68681 DUART data sheet (Motorola MC68681/D or the NXP SCN68681 equivalent, a PDF of about 0.5–1 MB) into `datasheets/`. Give the URL when asking. If it is declined, write from general MC68681 knowledge, and give the evidence of every D-entry as "no data sheet".

- [ ] **Step 1: Write the failing tests** in `tests/test_duart.cpp`. Use X1 = 3 686 400 unless a test says otherwise.
  - `duart_reset_state`: `ivr() == 0x0F`. ISR reads 0. SRA has TxRDY = 0 (the transmitter is disabled). `outputPins() == 0xFF`. `irq()` is false.
  - `duart_mr_pointer`: writing reg 0 twice sets MR1A then MR2A, and two reads return them in the same order. CRA command 0x10 points back at MR1A.
  - `duart_tx_character_timing`: MR1A = 0x13 (8 bits, no parity), MR2A = 0x07 (1 stop), CSRA = 0xBB (9600), CRA = 0x05 (enable TX and RX), then THRA = 0x55.
    - Right after the write, TxRDY = 1 and TxEMT = 0.
    - After `advance(3839)`, `takeTransmitted(0)` is empty.
    - After one more clock it is `{0x55}`, and TxEMT = 1.
  - `duart_rx_fifo_and_overrun`: same set-up, then `receive(0, b)` for b = 1..5 with no reads in between, and `advance(5 * 3840)`.
    - RHRA reads 1, 2, 3 in that order.
    - SRA had OE set before the reads, and `overruns(0) == 1`.
    - CRA command 0x40 (reset error status) clears OE.
  - `duart_rx_disabled_drops_bytes`: with the receiver disabled, a received byte never reaches RxRDY, even after it is enabled.
  - `duart_counter_mode_ready`: ACR = 0x30 (counter, X1/16), CTUR/CTLR = 0x09C4 (2500), read reg 14 (start).
    - After `advance(2500 * 16 - 1)`, ISR bit 3 = 0. After 1 more clock it is 1.
    - Reading reg 15 (stop) clears it.
    - With IMR bit 3 set, `irq()` follows ISR bit 3.
  - `duart_timer_mode_period`: ACR = 0x60 (timer, X1), preload 100. ISR bit 3 sets with the data sheet's period: the test asserts the cycle count the sheet gives.
  - `duart_op_pins_inverted`: write reg 14 = 0x40 and `outputPins()` bit 6 = 0. Write reg 15 = 0x40 and it is 1 again.
  - `duart_ip_change_interrupt`: ACR bit 0 enables IP0 change. `setInputPins` toggling IP0 sets IPCR bit 4 and ISR bit 7. Reading IPCR clears ISR bit 7.
  - `duart_rx_bit_clocks`: with X1 = 4 000 000 and the C/T in timer mode from X1 with preload 4 as the RX clock (CSRA = 0xDD), `rxBitClocks(0) == 128`. That is 4 000 000 / (2 · 4) = 500 kHz for the 16× clock.
  - `duart_unsupported_mode_counted`: MR2A = 0x47 (auto-echo) gives `unsupportedWrites() == 1`.

  ```cpp
  // Board: Board::frame() becomes otis.runFrame() followed by route().
  void Board::route(const OtisFrame& f, int16_t& mainL, int16_t& mainR);  // TR1 routing + esp.advance(89)

  struct RomSet {  // file images, unmodified
      std::vector<uint8_t> osUpper, osLower;   // 0x20000 and 0x10000 bytes
      std::vector<uint8_t> u25, u26, rom2, rom3;
  };
  enum class Device : uint8_t { Otis, Esp, Duart, Unmapped, Iack };
  struct BusEvent {
      uint64_t cycle;   // cpu.totalCycles() when the access is made
      uint32_t addr;    // 24-bit address; Iack: the level
      uint16_t value;   // value read or written; Iack: the vector answered
      uint8_t size;     // 1 or 2
      bool write;
      Device dev;
  };
  constexpr uint32_t kCpuHz = 15'238'090, kDuartHz = 4'000'000;  // K3
  constexpr int kSlotClocks = 16;                                // K3, K4
  class Machine {
  public:
      // nullptr on a wrong size, with err naming the file ("OS upper", "OS lower", "u25", ...).
      static std::unique_ptr<Machine> create(const RomSet& roms, std::string& err);
      void runFrame(int16_t& mainL, int16_t& mainR);  // until OTIS latches the next frame
      uint64_t cycles() const;                        // CPU cycles since power-on
      uint16_t peek16(uint32_t addr) const;           // ROM and RAM only, devices read 0, no side effects
      std::function<void(const BusEvent&)> onBusEvent;  // the bus trace; off when empty
      m68k::Cpu& cpu();
      Board& board();
      duart::Duart& duart();
  };
  ```
- The `Machine` is its own `m68k::Bus`. Power-on resets the CPU and the devices. `resetPeripherals()` resets the K14 set.

    - zero `Device::Unmapped` events during the boot;
    - `duart().unsupportedWrites() == 0`;
    - zero byte accesses to OTIS, and zero even-byte accesses to the ESP or the DUART (count them from the trace).
  - `ks32_firmware_boot_runs_the_esp`: `!board().esp().halted()` and `board().esp().serialControl() == 0x63` (findings C).
  - `ks32_firmware_boot_is_deterministic`: `traceHash` over the first `kBootMs` is equal for two fresh machines.

- [ ] **Step 2: Run them and observe.** Expected: most fail. Run `ks32emu boot --ms 5000 --trace unmapped,iack,duart` and read the summary. The firmware is stuck when no new event kind appears.

- [ ] **Step 3: Settle each fact by evidence, one at a time,** in this order. For each, try only the candidates listed. Prefer the one under which the firmware gets further: new device accesses appear, and fewer unmapped, fault-vector or spurious events. Use a scratch harness (not committed) for sweeps.
  1. **K1 memory map.** For each unmapped address the firmware touches, decide whether it is:
     - a RAM mirror;
     - a RAM size probe;
     - a device mirror; or
     - a device not yet modelled (stop and report).

     For the low-memory overlay and the RAM mirror, compare the provisional map with these two: (a) a separate RAM at 0x000000; (b) the overlay ending at the first access outside 0–7. The service manual (64 KB, chips U28 and U33) bounds the RAM size.
  2. **K2 interrupt map.** Try OTIS and DUART INTR on levels 1–6, and IACK answered by `duart().ivr()` or by autovector.
     - The right wiring takes no vector 24 or 15 and shows none of events 138 or 145 (spurious interrupt, unknown DUART interrupt).
     - It also gets furthest.
     - The IVR and IMR values the firmware writes are recorded.
  3. **K15 ESPHALT polarity.** Wire OP6 to `Esp::setHaltPin` both ways. The right one leaves the ESP running after boot and gives no event 33 ("bad ESP chip") or 40.
  4. **K14 RESET line.** Record whether the firmware executes RESET at all (vector counts, with an `Iack`-style counter if needed). If it does, decide which devices reset by the same "gets further" rule.
  5. **K9 wait states.** Change nothing unless a failure points to timing. Record "no evidence of wait states" otherwise.
  6. **K3 clocks.** Record the C/T mode and preload of the boot clock test from the DUART write summary, plus the resulting `activeVoices()`.
