# KS-32 JUCE App Implementation Plan (Plan 7)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A standalone Windows app (and a smoke-tested VST3) that boots the user's OS v3.01 on the emulated KS-32, plays it from the Q25, and shows the firmware-driven front panel as the approved artboards draw it.

**Architecture:**
- **The machine becomes real-time safe** (Task 1). The DUART and Panel byte queues become fixed rings, `PanelState` becomes fixed-size, and MIDI in is bounded. The Plan 6 hashes must not move.
- **A JUCE-free engine, `ens_app`** (Task 2), in `src/app/`. It owns one `Machine` and one `Resampler`, takes MIDI with sample offsets and GUI events through a fixed ring, renders host-rate audio, and publishes a panel snapshot.
- **The JUCE layer** (Tasks 4–7), in `app/`. It uses JUCE's stock Standalone wrapper plus VST3 through `juce_add_plugin`. One `AudioProcessor` owns the engine; the editor draws the panel from a JUCE-free layout table (`src/app/panel_layout.h`) transcribed from the artboard.
- **The transport-code hunt** (Task 3) is a bounded experiment with a scratch harness. It runs headless.

**Tech Stack:**
- C++17 and CMake 3.20+, with `tests/check.h`.
- JUCE 8.0.15, fetched by CMake `FetchContent`, MSVC x64 only, behind `ENS_BUILD_APP`.
- The existing `ens_player::Resampler`.

**Spec:** `docs/design/2026-10-28-ks32-juce-app-design.md` ("design"), approved 2026-10-28.
- It details §7.5 of the umbrella design `docs/design/2026-10-21-ks32-machine-and-juce-app-design.md`.
- Layout references: `docs/design/mockups/ks32-app-front-panel.dc.html` and `docs/design/mockups/ks32-app-settings.dc.html` ("the artboards").

## Global Constraints

- **Emulation stays pure.** `src/duart` and `src/ks32` keep Plan 6's rules: no JUCE, no OS calls, no threads, no file I/O, no mutable statics, and no `float` or `double`.
- **`src/app` is JUCE-free and OS-free.** It has no file I/O. It may use `float`, `std::atomic` and `std::mutex`.
- **Determinism.** The Plan 6 hashes stay identical on both builds:
  - boot trace `d2afd0fed8861cbd`;
  - render `2bae46b3acc34cd0`;
  - `ks32emu render tests/data/player_smoke.mid` PCM `a479ba867298cc55`.
- **Builds.** Everything except `app/` builds without warnings with VS 2022 x64 (`build-msvc/`, `/W4`) and MinGW g++ 14 plus Ninja (`build/`, `-Wall -Wextra`). The MinGW executables run from PowerShell with `C:\winlibs\mingw32\bin` on PATH. `app/` builds only with `-DENS_BUILD_APP=ON` on MSVC x64, without warnings from our own files.
- **Real time.** Once booted, nothing the audio thread calls may allocate, lock (other than `try_lock`) or wait. `ens_rt_tests` enforces this (Tasks 1 and 2).
- **No decompiling** (the user's ruling, 2026-10-23):
  - facts come from the service manual, the datasheets and the running firmware;
  - nothing ROM-derived is committed.
- **Never committed:** ROMs, traces, firmware listings, service-manual images, `docs/Ensoniq_KS32_Top.png`, `session_memory.json`, JUCE sources and build outputs.
- **Downloads.** Each needs the user's explicit permission. Fetching JUCE (Task 4, Step 0) is the only one planned. The controller asks before it.
- **ROM tests** use `ENS_ROM_DIR`. Without the ROMs a test prints `  skip: ROMs not found` and passes.
- **Branding.** The app says "KS-32" only, with no Ensoniq logo or name in the UI. The JUCE company name is "KS-32 Emulator", the manufacturer code `Kemu` and the plugin code `Ks32`.
- **Decisions.** Every choice the references do not settle gets two things:
  - a `// DECISION A<n>: <one line>` comment at the point of use;
  - a `docs/decisions.md` entry `## A<n>: <title>`, in the K entries' format, under a new `# KS-32 app` heading.

  Defaults are in the table below.
- **Stop and ask.** If the evidence or the code contradicts the design, the implementer stops and reports.
- **Branch.** Work on `plan7-juce-app` in a worktree, and commit after each task.

## Decision Defaults

| Id | Topic | Default | Task |
|---|---|---|---|
| A1 | MIDI-in bound | The DUART receive queue holds 1024 bytes per channel. Bytes beyond it are dropped, newest first, and counted (`Duart::rxDropped(ch)`). | 1 |
| A2 | Transmit and panel rings | DUART sent-bytes ring of 256 per channel, and Panel to-CPU ring of 256. When full, the newest byte is dropped and counted. The machine drains the panel channel every slot. The engine drains MIDI out every block and discards it, counting bytes. | 1, 2 |
| A3 | MIDI timing in a block | A MIDI byte at output offset `o` of a block enters the machine before machine frame `floor(o * 29762 / outRate)` of that block. The block's MIDI store holds 1024 bytes; extra bytes are dropped and counted. | 2 |
| A4 | GUI event timing | Posted events are applied at the start of the next block, in post order. The queue holds 256; `post` returns false when it is full. | 2 |
| A5 | Snapshot hand-off | The audio side publishes under `std::mutex::try_lock` and skips a block if the GUI holds the lock; the GUI locks normally. This replaces the design's sequence counter (§6.2): simpler, race-free, and the audio side never waits. | 2 |
| A6 | Booted | `Snapshot::booted` is true once the engine has run `kBootMs` of emulated time. | 2 |
| A7 | Display glyphs | Codes 0x20–0x7E are drawn as ASCII. 0x00–0x1F and 0x7F are drawn blank, and the debug overlay shows them as hex. | 6 |
| A8 | Blink | 2 Hz at 50 % duty, for display and LEDs alike, from the message-thread clock. | 6 |
| A9 | Chord latch | A right-click or Shift-click latches a button down until it is clicked again. A plain press is sent on mouse-down and its release on mouse-up, wherever the mouse is. Losing focus releases unlatched buttons. | 6 |
| A10 | Strike | Key strike = 1 + round(126 × y / keyLength), where y is the distance from the key's back edge; the front is loud. | 7 |
| A11 | Memory saving | Memory is saved on close and every 60 s, never before `booted`. Each write goes to `<file>.tmp` and then replaces the file. Erase loads 64 KB of zeros after a confirmation. | 5 |
| A12 | MIDI bytes passed | Every byte of every `MidiBuffer` message, sysex and real-time included, as the real MIDI IN jack would receive it. | 4 |
| A13 | Default window | 1360 × 480, resizable from 1020 × 360 upward, with the aspect ratio fixed at 2040:720. | 6 |
| A14 | Transport codes | Settled by Task 3, as found or not found. | 3 |

## Review Focus

1. **The audio thread stalls.** This covers the GUI reading the snapshot during a block, the autosave asking for RAM, and a MIDI flood. The audio callback must never allocate or wait. Tests: `rt_machine_runframe_does_not_allocate` (Task 1) and `rt_engine_render_does_not_allocate` (Task 2).
2. **The device changes mid-run.** The rate changes from 48 000 to 44 100 Hz, or the host asks for a block larger than `prepare`'s `maxBlock`. The engine must keep playing without allocating or overrunning, and must render oversize blocks in pieces. Test: `engine_render_larger_than_prepared_block` (Task 2).
3. **A stuck button.** A mouse released outside the button, or the window losing focus while a button is held, must still send the release. Otherwise the firmware sees the button held and later chords fail. Verified by Task 6, Step 5 (manual), with the A9 rules in code.
4. **Bad ROMs or memory.**
   - A missing or wrong-size ROM, or a changed ROM folder, gives the display message, not a crash.
   - A memory file of the wrong size is reported and ignored, and the machine boots cold.
   - Closing during the boot does not overwrite the memory file.

   Test: `engine_create_rejects_wrong_rom_size` (Task 2). The rest is checked by Task 5, Step 6 (manual).
5. **MIDI floods.** Several kilobytes of sysex in one block are dropped and counted. They do not corrupt later bytes or allocate. Test: `engine_midi_overflow_is_counted` (Task 2).

- Consumes: Task 1's pop APIs, `PanelState`, `ramImage()`, and `Resampler(double inRate, double outRate, int channels)`.
- Produces, in `namespace ens::app`:

```cpp
template <class T, size_t N> class SpscRing {  // one producer thread, one consumer thread
public: bool push(const T&); bool pop(T&); };
struct Event { enum class Kind : uint8_t { Button, Key, Analog };
    Kind kind; uint8_t id; bool down; uint16_t value; };
// Button: id = ks32::Button code. Key: id = note, value = strike. Analog: id = ks32::Analog, value = raw.
struct Snapshot { ks32::PanelState panel{}; bool booted = false; uint64_t frames = 0;
    uint32_t midiDropped = 0; uint64_t midiOutBytes = 0; };
class Engine {
public:
    static std::unique_ptr<Engine> create(const ks32::RomSet&, std::string& err);
    // Message thread, audio stopped:
    void prepare(double outRate, int maxBlock);         // allocates the resampler and buffers
    bool loadRam(const std::vector<uint8_t>& img, std::string& err);
    ks32::Machine& machine();                            // tests, and the RAM at shut-down
    // Message thread, audio running:
    bool post(const Event&);                             // false when the queue is full (A4)
    Snapshot snapshot() const;                           // A5
    void requestRam();                                   // the next block copies the RAM
    bool takeRam(std::vector<uint8_t>& out);             // true once a requested copy is ready
    // Audio thread:
    void midi(int offset, const uint8_t* data, int size);  // before render, offsets in this block (A3)
    void render(float* l, float* r, int frames);         // any frames >= 0; pieces of maxBlock
};
```
